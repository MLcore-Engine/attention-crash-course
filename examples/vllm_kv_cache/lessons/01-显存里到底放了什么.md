# 第 1 课 显存里到底放了什么

这一课先算出一份缓存的形状，再读创建它的代码。所有源码固定在 vLLM v0.11.0，提交为 `b8b302cde434df8c9289a2b465406b47ebab1c2d`。

## 固定一组能手算的参数

| 参数 | 本次取值 |
|---|---:|
| attention 层数 | 2 |
| 每层 KV 头数 | 2 |
| 每个头的维数 | 32 |
| GPU 缓存精度 | BF16，每个元素 2 字节 |
| 每块可放的 token 数 | 16 |
| 物理块数 | 8，块号 0～7 |
| A 的 prompt 长度 | 17 个 token，位置从 0 开始 |

这些是用于追踪地址的教学参数，K/V 数值由 CPU 例子构造。真实模型会在每一层用投影矩阵生成各自的 K/V。使用不同 KV 头数、维数或量化格式时，按实际规格重算。

## 从一行公式读出每块的字节数

源码第 57～66 行。[source/vllm/v1/kv_cache_interface.py](../upstream/source/vllm/v1/kv_cache_interface.py#L57)

<!-- source: upstream/source/vllm/v1/kv_cache_interface.py:57-66 -->
```python
@dataclass(frozen=True)
class AttentionSpec(KVCacheSpec):
    num_kv_heads: int
    head_size: int
    dtype: torch.dtype

    @property
    def page_size_bytes(self) -> int:
        return 2 * self.block_size * self.num_kv_heads * self.head_size \
                * get_dtype_size(self.dtype)
```

| 源码行 | 逐行理解 |
|---|---|
| 57～61 | `AttentionSpec` 保存一层的 KV 规格，继承的 `block_size` 是每块 token 数。 |
| 64 | 页的字节数是一个计算出来的属性。 |
| 65 | 最前面的 2 数 K 和 V。接着依次乘 16 个 token、2 个 KV 头和每头 32 个元素。 |
| 66 | 乘缓存 dtype 的元素大小。BF16 取 2 字节。 |


把这几行代入本例。

```text
每 token、每层的 KV = 2 × 2 × 32 × 2 = 256 B
每层、每块的 KV     = 16 × 256 = 4096 B
同一块号跨两层      = 2 × 4096 = 8192 B
8 个块号跨两层      = 8 × 8192 = 65536 B
```

同一个块号会用于该 KV cache group 中各层对应的缓存区域。例如块号 1 对应第 0 层的一页，也对应第 1 层的另一页，各层保留自己的数据。

## 启动时怎样决定有多少块

本版本先 profile 模型与运行时开销，再把可供 KV 使用的字节数交给缓存规划器。下面摘出 profile 之后实际计算剩余预算的一行。

<!-- source: upstream/source/vllm/v1/worker/gpu_worker.py:279-280 -->
```python
        self.available_kv_cache_memory_bytes = self.requested_memory \
            - profile_result.non_kv_cache_memory
```

| 源码行 | 逐行理解 |
|---|---|
| 279 | `requested_memory` 是当前实例允许使用的显存预算。 |
| 280 | 减去 profile 测出的权重、激活和其他非 KV 开销，留下 KV 预算。完整 profile 过程在同文件 222～306 行。 |


源码第 824～827 行。[source/vllm/v1/core/kv_cache_utils.py](../upstream/source/vllm/v1/core/kv_cache_utils.py#L824)

<!-- source: upstream/source/vllm/v1/core/kv_cache_utils.py:824-827 -->
```python
    num_blocks = int(available_memory // page_size // num_layers)
    num_blocks = max(num_blocks, 0)
    num_blocks = may_override_num_blocks(vllm_config, num_blocks)
    return num_blocks
```

| 源码行 | 逐行理解 |
|---|---|
| 824 | 在各层页大小一致的普通布局中，按每层页字节数、层数向下取整得到块数。本例为 `65536 // 4096 // 2 = 8`。 |
| 825 | 剩余显存太少时，把结果下限约束为 0。 |
| 826 | 调试配置可以覆盖自动算出的块数。 |
| 827 | 把块数交回配置生成流程。 |


这个公式的前提是这里展示的统一页规格。混合 full attention、sliding window 或 Mamba 的规划代码位于同文件 `get_kv_cache_groups` 与 `get_kv_cache_config_from_groups`。完整快照已包含这些分支。

## 字节怎样被解释成 K/V

选用 FlashAttention 后端，先看它声明的逻辑形状。

源码第 85～100 行。[source/vllm/v1/attention/backends/flash_attn.py](../upstream/source/vllm/v1/attention/backends/flash_attn.py#L85)

<!-- source: upstream/source/vllm/v1/attention/backends/flash_attn.py:85-100 -->
```python
        if block_size % 16 != 0:
            raise ValueError("Block size must be a multiple of 16.")
        return (2, num_blocks, block_size, num_kv_heads, head_size)

    @staticmethod
    def get_kv_cache_stride_order() -> tuple[int, ...]:
        # `stride_order` indicates the permutation that gets
        # us from `get_kv_cache_shape` to the actual memory layout we want.
        cache_layout = get_kv_cache_layout()
        if cache_layout == "NHD":
            stride_order = (0, 1, 2, 3, 4)
        elif cache_layout == "HND":
            stride_order = (0, 1, 3, 2, 4)
        else:
            raise ValueError(f"Unknown cache layout format {cache_layout}.")
        return stride_order
```

| 源码行 | 逐行理解 |
|---|---|
| 85～86 | 本后端要求 block size 为 16 的倍数，本例取 16。 |
| 87 | 返回 `[2, blocks, tokens_per_block, kv_heads, head_dim]`。本例为 `[2, 8, 16, 2, 32]`，第一个 2 数 K/V。 |
| 90～93 | 再取后端使用的实际存储顺序。 |
| 94～95 | NHD 保持块内 `[token, head, dim]` 顺序。 |
| 96～97 | HND 将块内实际存储顺序改为 `[head, token, dim]`。 |
| 98～100 | 校验布局标签，然后返回维度排列。 |


源码第 3847～3856 行。[source/vllm/v1/worker/gpu_model_runner.py](../upstream/source/vllm/v1/worker/gpu_model_runner.py#L3847)

<!-- source: upstream/source/vllm/v1/worker/gpu_model_runner.py:3847-3856 -->
```python
                    kv_cache_shape = tuple(kv_cache_shape[i]
                                           for i in kv_cache_stride_order)
                    # Maintain original KV shape view.
                    inv_order = [
                        kv_cache_stride_order.index(i)
                        for i in range(len(kv_cache_stride_order))
                    ]
                    kv_caches[layer_name] = kv_cache_raw_tensors[
                        layer_name].view(dtype).view(kv_cache_shape).permute(
                            *inv_order)
```

| 源码行 | 逐行理解 |
|---|---|
| 3847～3848 | 按后端的 stride 顺序组织物理 shape。 |
| 3850～3853 | 算一个逆排列，让返回张量依然具有约定的逻辑 shape。 |
| 3854～3855 | `view(dtype)` 将字节解释成 BF16 等类型。`view(shape)` 为同一份存储建立维度。 |
| 3856 | `permute` 建立调整了 stride 的视图。这几步保留对原始缓冲区的引用。写 kernel 使用实际 stride 算地址。 |


NHD 下，每层 K 和 V 的逻辑区域分别为 `[8,16,2,32]`。一个 token 的一层 K 有 64 个元素、128 B，V 也有 128 B。

继续顺着 `initialize_kv_cache_tensors` 3926～3942 行，会看到先分配、再 reshape、最后 `bind_kv_cache`。绑定实现把缓存张量交给 runner 和相应的 Attention 层。读模型时可以从 `Attention.kv_cache` 找到刚才创建的张量。 [绑定实现](../upstream/source/vllm/v1/worker/utils.py#L265)

## CPU 的块对象保存什么

源码第 169～186 行。[source/vllm/v1/core/kv_cache_utils.py](../upstream/source/vllm/v1/core/kv_cache_utils.py#L169)

<!-- source: upstream/source/vllm/v1/core/kv_cache_utils.py:169-186 -->
```python
@dataclass
class KVCacheBlock:
    """KV-cache block metadata."""
    # Block ID, ranging from 0 to num_gpu_blocks - 1.
    block_id: int
    # Reference count.
    ref_cnt: int = 0
    # The hash key (block hash + group id) of the block, only available
    # when the block is full and cached.
    _block_hash: Optional[BlockHashWithGroupId] = None

    # Used to construct a doubly linked list for free blocks.
    # These two attributes should only be manipulated by FreeKVCacheBlockQueue.
    prev_free_block: Optional["KVCacheBlock"] = None
    next_free_block: Optional["KVCacheBlock"] = None

    # Whether the block is a null block that should never be cached.
    is_null: bool = False
```

| 源码行 | 逐行理解 |
|---|---|
| 169～170 | 每个物理块号对应一个 Python 元数据对象。 |
| 173 | `block_id` 标识刚才 GPU 缓冲区中的页。 |
| 175 | `ref_cnt` 记录有多少个活跃请求引用这一块。 |
| 178 | 完整前缀块的查找键，组合了 block hash 与 group id。 |
| 182～183 | 将空闲块连接成双向链表，支持快速摘出命中的空闲缓存块。 |
| 186 | `is_null` 标记占位块，下一段会看到 0 号被取出来作占位。 |

| 源码行 | 逐行理解 |
|---|---|

这时的具体状态是

```text
GPU 张量中的页号    0  1  2  3  4  5  6  7
CPU 空闲队列          1 → 2 → 3 → 4 → 5 → 6 → 7
前缀 hash 查找表    空
每个请求的块表     尚未建立
```

用 `python3 examples/vllm_kv_cache/lifecycle_demo.py` 可以看到第 0 步相同的打印结果。

本课自测。输入长到 17 个 token 时，`ceil(17/16)=2`，会用两个块号。按两层计算，共占 16384 B 的页空间，其中 15 个 token 位置尚未使用。下一课去看谁把这两个块号发给 A。
