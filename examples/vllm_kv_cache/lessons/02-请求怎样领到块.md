# 第 2 课 请求怎样领到块

沿用第 1 课的 16 token/block 和 8 个块号。A 的 prompt 是 token id `1,2,…,17`，对应位置 `0,1,…,16`。先观察 CPU 元数据怎样变化，GPU 写入在第 3 课。

## allocate_slots 怎样算这一轮需要的位置

源码第 258～286 行。[source/vllm/v1/core/kv_cache_manager.py](../upstream/source/vllm/v1/core/kv_cache_manager.py#L258)

<!-- source: upstream/source/vllm/v1/core/kv_cache_manager.py:258-286 -->
```python
        num_computed_tokens = (request.num_computed_tokens +
                               num_new_computed_tokens)
        num_tokens_need_slot = min(
            num_computed_tokens + num_new_tokens + num_lookahead_tokens,
            self.max_model_len)

        num_blocks_to_allocate = self.coordinator.get_num_blocks_to_allocate(
            request_id=request.request_id,
            num_tokens=num_tokens_need_slot,
            new_computed_blocks=new_computed_block_list,
            num_encoder_tokens=num_encoder_tokens,
        )

        if num_blocks_to_allocate > self.block_pool.get_num_free_blocks():
            # Cannot allocate new blocks
            return None

        # Touch the computed blocks to make sure they won't be evicted.
        if self.enable_caching:
            self.block_pool.touch(new_computed_block_list)
        else:
            assert not any(new_computed_block_list), (
                "Computed blocks should be empty when "
                "prefix caching is disabled")

        # Append the new computed blocks to the request blocks until now to
        # avoid the case where the new blocks cannot be allocated.
        self.coordinator.save_new_computed_blocks(request.request_id,
                                                  new_computed_block_list)
```

| 源码行 | 逐行理解 |
|---|---|
| 258～259 | 把过去已计算的 token 与这次新命中的前缀相加。A 首次为 `0+0=0`。 |
| 260～262 | 给本步新增 token 和 lookahead 分配位置，并限制在模型长度内。A 此次需要 `0+17+0=17` 个 token 的位置。 |
| 264～269 | 让 coordinator 按各缓存组算需要消耗多少空闲块。 |
| 271～273 | 空闲块不足时返回 `None`，让调度器决定等待或抢占。 |
| 276～277 | 先增加命中块的引用，把命中的空闲缓存块从可淘汰队列摘出来。A 目前没有命中。 |
| 278～281 | 缓存关闭时校验命中列表为空。 |
| 285～286 | 把刚命中的块接到该请求的块表。新块追加发生在下一段。 |


coordinator 对本例只有一个 group，负责把调用传给 `SingleTypeKVCacheManager`。它持有 `req_to_blocks`，即每个请求自己的块号列表。coordinator 的各层转发在 47～139 行。 [转发实现](../upstream/source/vllm/v1/core/kv_cache_coordinator.py#L47)

源码第 76～86 行。[source/vllm/v1/core/single_type_kv_cache_manager.py](../upstream/source/vllm/v1/core/single_type_kv_cache_manager.py#L76)

<!-- source: upstream/source/vllm/v1/core/single_type_kv_cache_manager.py:76-86 -->
```python
        num_required_blocks = cdiv(num_tokens, self.block_size)
        num_new_blocks = (num_required_blocks - len(new_computed_blocks) -
                          len(self.req_to_blocks[request_id]))
        # If a computed block of a request is an eviction candidate (in the
        # free queue and ref_cnt == 0), it will be changed from a free block
        # to a computed block when the request is allocated, so we also count
        # it as needed to be allocated.
        num_evictable_computed_blocks = sum(
            blk.ref_cnt == 0 and not blk.is_null
            for blk in new_computed_blocks)
        return num_new_blocks + num_evictable_computed_blocks
```

| 源码行 | 逐行理解 |
|---|---|
| 76 | `cdiv` 为向上取整除法，`cdiv(17,16)=2`。 |
| 77～78 | 总共需要 2 块，减去命中的块数和原有块数。A 两者都为 0，所以要新领 2 块。 |
| 83～85 | 命中的块如果当前在空闲队列里，马上就要被 pin 住，也要从空闲预算中扣掉。 |
| 86 | 返回本次会消耗的空闲队列额度，供上面的 271 行做准入检查。 |


例如另一个请求命中一个 `ref_cnt=0` 的块，还需新领一块，就会消耗两个空闲名额。其中一个来自复用，另一个来自新分配。第 4 课会实测这一点。

源码第 123～131 行。[source/vllm/v1/core/single_type_kv_cache_manager.py](../upstream/source/vllm/v1/core/single_type_kv_cache_manager.py#L123)

```python

        num_required_blocks = cdiv(num_tokens, self.block_size)
        num_new_blocks = num_required_blocks - len(req_blocks)
        if num_new_blocks <= 0:
            return []
        else:
```

|---|---|
| 123 | 取得 A 的块表，初始是空列表。 |

| 125 | 本例为 `2-0=2`。 |
| 126～127 | 现有尾块仍有空间时，返回空列表，本轮无需增加块号。 |

## BlockPool 怎样发出 1、2 号块

源码第 268～284 行。[source/vllm/v1/core/block_pool.py](../upstream/source/vllm/v1/core/block_pool.py#L268)

<!-- source: upstream/source/vllm/v1/core/block_pool.py:268-284 -->
```python
        if num_blocks > self.get_num_free_blocks():
            raise ValueError(
                f"Cannot get {num_blocks} free blocks from the pool")

        ret: list[KVCacheBlock] = self.free_block_queue.popleft_n(num_blocks)

        # In order to only iterate the list once, we duplicated code a bit
        if self.enable_caching:
            for block in ret:
                self._maybe_evict_cached_block(block)
                assert block.ref_cnt == 0
                block.ref_cnt += 1
        else:
            for block in ret:
                assert block.ref_cnt == 0
                block.ref_cnt += 1
        return ret
```

| 源码行 | 逐行理解 |
|---|---|
| 268～270 | 底层再次检查空闲量，直接调用底层领超额会抛错。正常调度入口在上层已检查。 |
| 272 | 从空闲队列头部取两个对象。初始队列为 1～7，所以得到 1 和 2。 |
| 275～277 | 开启前缀缓存时，重新使用一个空闲块前先撤销它的旧缓存键。本例两个块从未用过，没有旧键。 |
| 278 | 取出的块应当没有活跃请求引用。 |
| 279 | 领给 A 后，引用计数从 0 变成 1。 |
| 280～283 | 关闭前缀缓存时也会更新引用计数。 |
| 284 | 返回两个块对象。此处操作 CPU 元数据，GPU 张量继续沿用初始化时的那份存储。 |


这一轮结束后，CPU 记录的状态是

| 项目 | 值 |
|---|---|
| A 的块表 | `[1,2]` |
| 1 号引用数 | 1 |
| 2 号引用数 | 1 |
| 空闲队列 | `[3,4,5,6,7]` |
| 对应每层缓存的页 | A 的位置 0～15 对应页 1，位置 16 对应页 2 |

<!-- source: upstream/source/vllm/v1/core/kv_cache_utils.py:310-332 -->
```python
        if n == 0:
            return []
        assert self.num_free_blocks >= n
        self.num_free_blocks -= n

        curr_block = self.fake_free_list_head.next_free_block
        # Pop n blocks from the head of the list
        ret = []
        for _ in range(n):
            assert curr_block is not None
            ret.append(curr_block)
            last_block = curr_block
            curr_block = curr_block.next_free_block
            # Reset prev_free_block and next_free_block of all popped blocks
            last_block.prev_free_block = None
            last_block.next_free_block = None

        if curr_block is not None:
            # The queue is not empty, connect the fake head to
            # the new first block.
            self.fake_free_list_head.next_free_block = curr_block
            curr_block.prev_free_block = self.fake_free_list_head
        return ret
```

| 315 | 从哨兵头后面的第一个真实块开始。 |

## 新 token 来了，每次都领块吗

接下来让 A 从 17 个已计算 token 长到 18 个。需要的块数仍然是 `ceil(18/16)=2`，123～127 行得到 `num_new_blocks=0`，继续写第二块的下一个位置。

当已计算长度从 32 变为 33，才有 `ceil(33/16)=3`。这时需要多一块。例子会在 B 已经领走 3 号之后，让 A 从队头领到 4 号，于是块表为 `[1,2,4]`。

| A 已计算的 token 数 | 所需块数 | 最后一个已写位置 | 物理块与块内偏移 |
|---:|---:|---:|---|
| 17 | 2 | 16 | 2 号、offset 0 |
| 18 | 2 | 17 | 2 号、offset 1 |
| 32 | 2 | 31 | 2 号、offset 15 |
| 33 | 3 | 32 | 4 号、offset 0 |

一次采样得到输出 token，与这个 token 自己的 KV 写入之间还隔着一次 forward。例如 17 个 prompt token 的 prefill 产生输出 token 900，随后一轮才把 900 放在位置 17 输入模型，得到它的 K/V，并预测下一个输出。到响应结束时，最后采样的 token 可能还没有自己的 KV。因此这里按「已计算 token 数」描述缓存长度。

|---|---|

```python
    def append_row(
        self,
        block_ids: list[int],
        row_idx: int,
    ) -> None:
        if not block_ids:
            return
        num_blocks = len(block_ids)
        start = self.num_blocks_per_row[row_idx]
        self.num_blocks_per_row[row_idx] += num_blocks
        self.block_table.np[row_idx, start:start + num_blocks] = block_ids

    def add_row(self, block_ids: list[int], row_idx: int) -> None:
        self.num_blocks_per_row[row_idx] = 0
        self.append_row(block_ids, row_idx)
```

| 源码行 | 逐行理解 |
|---|---|
| 54～55 | 本轮没有新增块时直接返回。 |
| 56 | 新增块个数。 |
| 57 | 找到该行已有数据的结尾。 |
| 58 | 更新该行已使用的块号数量。 |
| 59 | 在 CPU 块表矩阵中追加整数块号。 |
| 61～63 | 新请求先将这一行的长度清零，再复用上面的追加方法。 |


本课自测。A 有块表 `[1,2,4]` 时，逻辑位置 32 必须写到 4 号物理块。物理块可以相隔很远，下一课的地址翻译负责让 kernel 找到它。
